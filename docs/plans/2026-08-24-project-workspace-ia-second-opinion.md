# Project Workspace IA Second Opinion

> 日期：2026-08-24
> 角色：与实现团队隔离的中立高级 UX / 信息架构评审
> 范围：`ProjectWorkspacePage.tsx`、`projectWorkspaceRouting.ts`、项目组件，以及 `http://127.0.0.1:3011` 当前可见项目工作区
> 约束：本报告在未阅读 `2026-08-24-project-workspace-ia-consolidation.md` 的前提下先形成独立结论；与既有方案的对照只放在最后一节。

## 1. 结论先行

当前工作区不是单纯“Tab 太多”，而是把对象、观察视角和用户任务混在同一级：14 个一级入口中，`目标与任务` 与 `工作项` 是同一对象的两个入口；`能力中心` 与 `能力矩阵` 是同一权限模型的编辑态和交叉表；`工作区`、`交付里程碑`、`Git 历史与恢复` 是同一交付链的不同视图；`运行控制`、`A2A Mesh`、`项目事件审计` 又分别重复呈现运行和事件。与此同时，`项目设置` 既是页头按钮，又以“运行与安全策略”出现在一级导航中，Git 页还承载了仓库设置。

建议把 14 个一级 Tab 收敛为 6 个任务域，加 1 个独立设置入口：

1. 概览
2. 工作
3. 协作
4. 交付
5. 团队
6. 活动
7. 项目设置（页头工具入口，不计入主导航）

收敛不等于把所有内容做成长页。每个任务域用二级视图表达对象的不同工作模式；每类原始记录只设一个“权威浏览载体”，其他页面只保留有上限的摘要、状态和深链。

## 2. 审计方法与证据边界

本次评审以六条真实任务流为判据，而不是以页面名是否相似为判据：规划推进、日常执行、异常排查、交付验收、团队与能力管理、版本追溯。

代码证据：

- 当前路由声明 14 个一级 Tab，见 `frontend/src/features/projects/projectWorkspaceRouting.ts:1-15`。
- 左侧导航同样渲染 14 个入口，分为“运行与协作”和“治理与追溯”，见 `frontend/src/features/projects/ProjectWorkspacePage.tsx:227-311`。
- 每个 Tab 又拥有独立 URL 参数集合，说明当前 IA 已将同一对象的视图固化为多个平级信息孤岛，见 `frontend/src/features/projects/projectWorkspaceRouting.ts:19-77`。
- 内容分发由一个 14 分支的 `switch` 完成，见 `frontend/src/features/projects/ProjectWorkspacePage.tsx:1311-1486`。

可见页面证据来自 3011 上的项目“真实角色协作验收·发布变更风险平台·0823”。这是一次时点走查，数字会变化，但结构性重复不依赖这些具体数字：

- 驾驶舱同时显示 7 个工作项、7 个风险、6 名成员、258 个事件，并给工作项和风险各自分页。
- “目标与任务”以依赖图/看板展示同一批 7 个工作项；“工作项”一级页又用 7 列列表重复展示它们。
- 抽查工作项 M4 时，详情顶部同时显示 `3 Run / 22 事件`、14 个关联会话、15 个代码/文件变化、10 项证据；这些记录又分别出现在执行、会话、变化、审批四个分区。
- 项目成员页先显示 27 次历史运行摘要；选中负责人后，谱系图显示最近 8/共 15 次运行，同页下方又列出同一成员的 15 次运行。
- 能力中心当前没有 Skill/MCP 绑定，却在同页继续显示 14 个项目工具；能力矩阵再把同一 14 个工具按 6 名成员展开。
- Git 页在 20 条提交历史之前先显示仓库来源、远端列表、添加远端、从远程初始化；历史浏览和设置编辑混在同一滚动面。
- A2A Mesh 显示 45 条 A2A 事件；审计页显示 258 条全量事件，前者是后者的过滤子集。

## 3. 按任务流审计

| 任务流 | 用户要回答的问题 | 当前路径与阻力 | 结论 |
|---|---|---|---|
| 规划推进 | 目标拆成了什么、依赖是什么、谁负责、下一步是什么 | 驾驶舱预览 → `目标与任务` 图/看板 → `工作项`列表 → 工作项详情；同一工作项有两个一级入口 | 合并为“工作”；列表、看板、依赖图是二级视图，详情是对象路由，不是一级 Tab |
| 日常执行 | 去哪里下达任务、看进行中工作、处理 Run | 群聊、工作项、运行控制分别提供消息、任务、运行；详情中的“执行与事件”又重复 Run | 保留“协作”和“工作”；全局 Run 控制归“活动”，工作项内只显示关联运行摘要和深链 |
| 异常排查 | 哪一步失败、由谁触发、会话和上下文是什么 | 驾驶舱风险可能跳会话、工作项或审计；工作项执行混排 Run/事件；A2A、全局 Run、审计分别再展示一遍 | “活动”成为统一排查入口：Runs 与 Events 两个二级视图；风险卡必须深链到唯一关联对象 |
| 交付验收 | 验收条件是否满足、证据和变更是什么、能否批准 | 工作项“上下文与验收”和“证据与审批”都出现验收信息；执行结果又在审批证据里重复；文件、Commit 分两个列表 | 工作项详情保留独立“验收”模式，但以验收条件为主轴映射证据；变更按 change set 分组，避免文件/Commit 双列表 |
| 团队与能力管理 | 谁在岗、用什么配置、能做什么 | 成员页混入运行谱系、快照编辑、运行列表；能力中心与能力矩阵平级，项目工具又是另一套列表 | 合并为“团队”，二级视图为成员、能力、访问矩阵；成员活动只做摘要并跳“活动”过滤结果 |
| 版本追溯 | 交付物在哪个版本、为何变化、如何恢复 | 工作项变化、工作区、里程碑、Git、审计均可看到局部版本关系；Git 页还混入仓库设置 | “交付”统一工作区、里程碑、版本历史；仓库来源/远端移动到设置；审计保留不可变事件而非替代版本历史 |

## 4. 重复项、证据与唯一归属

### 4.1 工作项：一个对象被拆成两个一级入口

证据：

- `WorkBoard` 同时提供依赖图和看板，并从节点/卡片进入详情，见 `ProjectWorkspacePage.tsx:2004-2005`、`2081-2104`、`2198-2276`。
- `WorkItemList` 再用状态、优先级、负责人、执行进度、验收进度、更新时间展示同一对象，见 `ProjectWorkspacePage.tsx:2507-2703`。
- 当前 `WorkBoard` 的选择动作直接跳到 `detail` 一级 Tab，见 `ProjectWorkspacePage.tsx:1321-1329`。

重复：对象列表、状态、负责人、进度、验收摘要、进入详情 CTA。

唯一归属：一级“工作”。二级视图为“列表 / 看板 / 依赖”。三者共享同一筛选、排序和对象选择状态。选中工作项进入唯一 canonical detail route，并能返回原视图和筛选。

### 4.2 驾驶舱：摘要变成了第二套浏览器

证据：

- 驾驶舱已有项目目标、负责人、成员、验收标准、项目进度和 4 个指标，见 `ProjectWorkspacePage.tsx:1819-1888`。
- 工作项与风险各自使用分页列表，见 `ProjectWorkspacePage.tsx:1782-1801`、`1889-1976`。

重复：完整工作项分页、完整风险分页，与工作/活动页面争夺浏览职责。

唯一归属：概览只保留 4 个项目级信号、最多 5 个“下一步工作”和最多 5 个“需关注异常”。不分页；“查看全部”分别进入工作或活动，并携带过滤条件。

### 4.3 工作项详情：五个分区重复相同执行证据

证据：

- 当前五个分区为“上下文与验收、执行与事件、关联会话、代码与文件变化、证据与审批”，见 `ProjectWorkspacePage.tsx:3054-3075`。
- 上下文分区同时承担说明、依赖、验收条件、指派、状态、优先级、创建 Run 与保存，见 `ProjectWorkspacePage.tsx:3088-3203`。
- 执行分区混排 Run 与事件，并各自提供会话入口，见 `ProjectWorkspacePage.tsx:3204-3276`。
- 关联会话从 DTO sessions、Run、事件再次合成列表，见 `ProjectWorkspacePage.tsx:2969-3010`、`3277-3362`。3011 可见页中相同 session ID 多次出现，但卡片没有解释不同 anchor/run 的关系，用户会感知为重复。
- 代码与文件变化同时列文件和 Commit；抽查 M4 为 7 个文件和 8 个 Commit，两边大量一一对应，见 `ProjectWorkspacePage.tsx:3363-3494`。
- 证据与审批再次渲染执行结果、会话入口、Run/会话/Commit/文件计数，见 `ProjectWorkspacePage.tsx:3495-3644`。

建议收敛为四个详情模式：

1. 摘要：任务说明、依赖、验收条件、负责人、状态、优先级；唯一编辑/启动入口。
2. 活动：按 Run 分组的时间线；事件和会话作为 Run 的子记录，不再提供平级“执行”和“会话”列表。
3. 交付物：按一次变更/Commit 分组，组内列文件与 diff；不是“文件列表 + Commit 列表”两套分页。
4. 验收：以每条验收条件为行，映射证据、结果和缺口；退回/通过只出现在此模式。

工作项顶端可保留负责人、状态、优先级、最近运行、更新时间等 5 个固定事实，但各分区不得再次复述同一组总数。

### 4.4 成员页：运行记录在同页出现三次

证据：

- 成员页顶部汇总项目数字员工、在岗成员、历史运行，见 `ProjectWorkspacePage.tsx:4833-4852`。
- 选中成员后渲染 SnapshotLineageGraph，图中最多放入 8 个可追溯 Run，见 `ProjectWorkspacePage.tsx:4869-4908` 和 `components/ProjectGraphs.tsx:731-920`。
- 同一页下方又渲染成员 Run / Session History 完整分页，见 `ProjectWorkspacePage.tsx:5206-5260`。
- 图与运行列表之间还插入了三层快照解释、模型/指令/自主策略与 6 个事实，见 `ProjectWorkspacePage.tsx:4910-5204`。

重复：运行总数、运行节点、运行列表、会话 CTA。

唯一归属：成员详情负责身份、角色、在岗状态和项目快照配置；保留谱系图用于解释“源数字员工 → 项目快照 → Run 冻结快照”的版本关系，但只显示最近 3 个 Run 或仅显示冻结代次。完整运行列表及会话归“活动 > Runs”，成员页用“查看该成员全部活动”深链。

### 4.5 能力中心与能力矩阵：编辑态和观察态被做成两个产品区

证据：

- 能力中心已有类型/来源筛选、能力开关、项目工具成员选择与工具开关，见 `ProjectWorkspacePage.tsx:5931-6102`。
- 能力矩阵再次按能力 × 成员显示有效状态，见 `ProjectWorkspacePage.tsx:6107-6232`。
- 同一矩阵页又以项目工具 × 成员显示同一工具可用性，见 `ProjectWorkspacePage.tsx:6235-6372`。
- 项目工具的有效性解析在卡片和矩阵中复用同一 `projectToolResolution`，见 `ProjectWorkspacePage.tsx:5857-5918`、`6296-6339`；语义上本就是同一个访问模型。

重复：能力/工具名称、来源/适用成员、成员有效状态、是否可用。

唯一归属：一级“团队”下的“能力”对象域。二级或视图切换为“清单 / 访问矩阵”；Skill、MCP、项目工具是类型筛选。开关发生在清单或矩阵侧栏详情中，不能在清单无数据时再拼接一套独立项目工具分页。

### 4.6 A2A、Runs 与审计：过滤子集被复制成完整事件流

证据：

- A2A Mesh 同时包含网络图和 A2A 事件完整分页，见 `ProjectWorkspacePage.tsx:2393-2479`。
- 运行控制显示全局 Run 和暂停、继续、完成、重试等操作，见 `ProjectWorkspacePage.tsx:4157-4339`。
- 审计页对全量事件提供搜索、执行主体、事件类型筛选和分页，见 `ProjectWorkspacePage.tsx:7708-7858`。
- 工作项执行分区和成员运行列表又是上述数据的对象过滤结果。

重复：Run 状态、事件时间线、会话入口、执行主体、分页。

唯一归属：

- “活动 > Runs”是可操作的运行控制台，拥有暂停/继续/重试和运行会话。
- “活动 > Events”是不可变审计浏览器，拥有搜索和过滤。
- “协作 > A2A 网络”保留拓扑、边强度、成员关系和每条边的最近异常；完整 A2A 流用深链打开 `Events?channel=a2a`，不再复制分页时间线。
- 工作项、成员和里程碑只展示对象相关的最多 3 条最近运行/事件，以及“查看全部”过滤深链。

### 4.7 工作区、里程碑、版本历史与仓库设置

证据：

- 工作区是完整文件树、预览、编辑、下载和保存提交工具，见 `components/ProjectFileWorkspace.tsx:602-905`；这是独立的沉浸式任务，不是简单摘要。
- 里程碑卡同时汇总工作项、执行、交付文件、参与成员并可展开运行，见 `ProjectWorkspacePage.tsx:3936-4126`。
- Git 页既有仓库来源/远端/克隆设置，见 `ProjectWorkspacePage.tsx:7031-7331`，又有提交历史、详情、分支和恢复，见 `ProjectWorkspacePage.tsx:7443-7644`。
- 工作项“代码与文件变化”还提供跳转工作区/Git 的入口，见 `ProjectWorkspacePage.tsx:3416-3447`。

重复：文件、Commit、Run、工作项、会话在多个交付页面各自成列表。

唯一归属：一级“交付”，二级视图“工作区 / 里程碑 / 版本历史”。工作项交付物是该数据的上下文投影；里程碑是一组已冻结的工作项、版本和证据，不复制完整 Run 列表。仓库来源、远端和初始化迁移到“项目设置 > 仓库”，版本历史只保留提交、diff、分支与恢复。

### 4.8 项目设置：入口和保存边界重复

证据：

- 页头始终有“项目设置”按钮，并跳到 `policies`，见 `ProjectWorkspacePage.tsx:1513-1519`。
- 左侧又有一级“运行与安全策略”，见 `ProjectWorkspacePage.tsx:295-298`。
- 同一页面同时出现“保存策略”和“保存可见范围”，见 `ProjectWorkspacePage.tsx:6492-6575`、`6713-6814`。

重复：两个导航入口；一个屏幕内两个不一致的保存域；Git 远端另藏在历史页。

唯一归属：页头“项目设置”是唯一入口。二级设置为“常规与访问 / 运行与安全 / 仓库 / 模板发布”。每个二级设置页只有一个清晰保存域和一个主 CTA。

## 6. 信息预算

信息预算是避免下一轮“合并后又长成多个页面”的硬约束。

| 层级/页面 | 信息预算 |
|---|---|
| 一级导航 | 最多 6 个任务域；设置是唯一页头工具，不在侧栏重复 |
| 二级视图 | 每个一级域最多 3 个；设置最多 4 个 |
| 页面标题区 | 1 个主标题、最多 1 个主 CTA、最多 2 个次要动作；过滤不计 CTA |
| 概览 | 最多 4 个指标；每个预览列表最多 5 条；禁止分页 |
| 工作列表 | 默认最多 5 个可扫列：工作内容、状态/优先级、负责人、进度/验收、更新时间；长说明最多一行 |
| 工作项详情 | 顶部最多 5 个固定事实；4 个详情模式；每个模式一个明确任务；禁止在多个模式重复同一总数块 |
| 对象上下文活动 | 最多 3 条最近记录 +“查看全部”；全量分页只在活动域 |
| 成员详情 | 身份/角色/状态最多 5 个事实；快照配置每组最多 6 个字段；谱系最多 3 个最近 Run 节点，不再追加全量 Run 列表 |
| 能力 | 同一能力数据一次只显示清单或矩阵；类型/来源/状态最多一行筛选；每种集合只有一套分页 |
| 交付物 | 文件与 Commit 按 change set 分组；一组一个 Commit 头和文件子项，不提供两套独立分页 |
| 版本历史 | 仅一套提交列表 + 一个提交详情；仓库设置不得出现在历史滚动面 |
| 活动 | Runs 和 Events 分视图；每个视图一套过滤、一套分页；事件不在 A2A/成员/工作项再做完整分页 |
| 设置 | 每个二级页一个保存域、一个主 CTA；危险操作与常规保存分组并明确确认 |

## 7. 不应合并项与反例

### 7.1 Runs 不等于 Events

反例：失败 Run 需要“重试”，运行中 Run 需要“暂停/继续”；审计事件必须保持不可变，只能搜索和追溯。把二者混成一条时间线会把控制操作和证据浏览混淆。因此它们共享“活动”一级域，但保留两个二级视图。

### 7.2 项目群聊不等于 A2A 网络

反例：群聊是持续可写的多人协作空间；A2A 网络回答成员间调用关系、方向、频次和异常。两者都属于协作，但群聊不能被拓扑或事件列表替代，A2A 网络也不应降级成聊天筛选。

### 7.3 工作区不等于版本历史

反例：工作区需要树形浏览、预览、编辑和保存；版本历史需要 Commit 选择、diff、分支和恢复。二者共享“交付”域和深链，但不能合成一个同时编辑当前文件又恢复旧版本的单屏，否则上下文和风险等级冲突。

### 7.4 里程碑不等于 Commit

反例：Commit 是技术版本；里程碑是被业务确认的一组工作项、版本和证据。一个里程碑可关联多个 Commit，一个 Commit 也未必是交付节点。里程碑应引用版本，不应被 Git tag 样式的列表取代。

### 7.5 成员配置不等于能力矩阵

反例：成员详情编辑模型、指令、自主策略和生命周期；访问矩阵用于横向比较多人能力。把矩阵嵌进每个成员详情会失去跨成员比较，把全部成员配置塞进矩阵又无法承载复杂编辑。因此二者同属“团队”，但保持不同二级视图，并通过成员过滤互相深链。

### 7.6 工作项验收不等于项目里程碑验收

反例：工作项验收判断一项任务是否满足逐条标准；项目里程碑确认一个阶段交付包是否冻结。前者的通过/退回改变工作项状态，后者创建交付节点。两者可以共享证据组件，不能共用同一审批动作。

### 7.7 审计不应被“去重”成只有业务摘要

反例：一次 A2A 请求、送达、完成可能在业务摘要中被合成一条协作，但审计仍需保留三个不可变事件用于故障和责任追溯。应去除的是多个页面的重复浏览载体，不是底层审计记录。

## 8. 路由与详情载体原则

1. 每种核心对象只有一个 canonical route：work item、member、run、event、milestone、commit、file 各自唯一。
2. 视图状态用二级参数表达，例如 `section=work&view=board`，而不是再创造平级 Tab。
3. 上下文入口只携带 filter/anchor/returnTo。例如从工作项进入活动，应打开 `activity/runs?workItem=...&run=...`，返回时恢复原详情模式。
4. 当前 `projectWorkspaceTabUrlPatch` 会按 Tab 清理参数，见 `projectWorkspaceRouting.ts:83-100`；重构后应按一级域保留该域共享筛选，并只清除冲突对象参数。
5. 会话卡片的视觉身份至少包含 `session + anchor/run + relation`。若同一 session 因不同 Run/anchor 合法出现多次，必须显示“本 Run 起点”“证据消息”等区别，不能只重复同一个 session ID 和“打开会话”。
6. Drawer 只用于辅助核对且关闭后不丢主任务；需要连续浏览/比较的工作项、成员、Run、Commit 详情应有可复制、可返回的路由状态。

## 9. 可量化验收标准

### 导航与归属

- 一级任务入口从 14 个降到不超过 6 个；页头仅保留 1 个项目设置入口。
- 100% 当前入口都有迁移映射和兼容跳转；旧 URL 不出现空白页或丢失对象选择。
- 工作项只有 1 个 canonical detail route；从概览、列表、看板、依赖、里程碑进入同一工作项时 URL 对象身份一致。
- 仓库远端/初始化设置在版本历史页的可见控件数量为 0；全部位于“项目设置 > 仓库”。

### 去重

- work items、runs、events、commits、files、capabilities/tools 六类集合中，每类最多只有 1 个一级域提供全量分页浏览。
- 概览、成员、里程碑、工作项等上下文页的关联记录均不超过 3 条（概览预览不超过 5 条），且有明确“查看全部”深链。
- 同一屏不得同时出现“同一成员的 Run 谱系节点”和“同一成员的全量 Run 分页列表”。
- 能力清单与访问矩阵共享同一数据模型和过滤定义；同一视图不得同时出现两套工具/能力分页。
- 工作项交付物中，文件与 Commit 的两套平级分页改为 change-set 分组；抽查任意工作项，一个文件变化只在一个分组中出现一次。
- 工作项活动中，相同 `sessionId + runId + anchorMessageId` 的卡片重复数为 0；合法同 session 多 anchor 的卡片 100% 显示关系标签。

### 信息预算与动作

- 概览指标不超过 4 个，预览模块不分页。
- 任一页标题区主 CTA 不超过 1 个，次要动作不超过 2 个。
- 工作项详情模式不超过 4 个；固定事实不超过 5 个。
- 每个设置二级页只有 1 个保存域；保存后 toast 文案与按钮动作名称一致。
- 默认 1440px 桌面宽度下，用户无需横向滚动即可识别工作列表的 5 个核心字段；访问矩阵可使用明确的局部横向滚动并冻结首列。

### 六条任务流

- 规划推进：从概览到任一工作项详情不超过 2 次点击；在列表/看板/依赖间切换不丢筛选和选中项。
- 日常执行：从项目工作区进入群聊 1 次点击；从工作项创建/查看关联 Run 不超过 2 次点击。
- 异常排查：点击概览风险后 1 次跳转到具体 Run、Event、Work item 或 Session 锚点，不得只落到无过滤的全量页。
- 交付验收：从工作列表进入验收模式不超过 2 次点击；从一条验收证据打开对应 diff 或会话再增加不超过 1 次点击。
- 团队与能力管理：从团队入口到选中成员配置或访问矩阵不超过 2 次点击；矩阵可直接筛选成员和能力类型。
- 版本追溯：从里程碑或工作项交付物到对应 Commit 详情不超过 2 次点击；恢复动作必须显示目标 Commit、当前 HEAD 和影响说明。

### 可用性验证

- 以至少 5 名非实现团队用户执行上述六项任务；每项首次成功率不低于 80%，中位完成时间相较当前 IA 至少下降 25%。
- “应该去哪个一级入口”的首次选择正确率不低于 85%；`目标与任务/工作项`、`能力中心/能力矩阵`、`项目设置/运行与安全策略`三组旧歧义的误选率低于 10%。
- 所有二级切换、对象选择、过滤和 Drawer 打开状态支持浏览器前进/后退；自动化路由验收覆盖率 100%。

## 10. 与既有 consolidation 方案的最后对照

对照对象为 `docs/plans/2026-08-24-project-workspace-ia-consolidation.md`。该文档前半部分曾建议把 Git 与审计合成“变更与审计”，但其第十节第二轮审计明确改为二者不合并，并将最终日常一级入口定为 10 个；以下以第十节的最终结构为主，不把已被文档自身修正的第一轮结论当作最终方案。

### 10.1 一致点

1. **工作对象归一。** 两份报告都认为“目标与任务 + 工作项”必须合并，依赖图、看板、列表是同一集合的视图，工作项详情是子路由。
2. **驾驶舱去列表化。** 都认为摘要一旦分页就成为第二个列表页；驾驶舱只应显示固定上限的行动与问题，并深链权威页面。
3. **能力入口归一。** 都建议合并能力中心、能力矩阵和成员工具编辑；成员详情只显示授权摘要，不保留第三个编辑面。
4. **项目设置下沉。** 都认为页头“项目设置”与一级“运行与安全策略”是同一低频任务，一级策略入口应移除。
5. **A2A 事件流去重。** 都保留协作关系图的独特语义，但移除图下完整事件分页；原始事件回到审计/活动事件页。
6. **成员页移除完整 Run 长列表。** 都保留快照/谱系语义，但认为完整成员 Run 历史应由运行页面承担。
7. **Git 与审计不应语义合并。** 本报告虽把二者分别放在“交付 > 版本历史”和“活动 > Events”，但同样坚持 Git 可恢复、审计只读取证的权限与动作边界，反对把它们做成同一数据页。
8. **不合并对象边界一致。** 群聊与追溯会话、工作项与 Run、工作区与 Git、里程碑与 Commit、成员快照图与协作关系图均应保持独立语义。
9. **URL 与抽屉原则一致。** 都要求对象、二级视图、过滤和锚点可恢复；会话入口复用统一抽屉并定位准确消息。
10. **量化验收方向一致。** 都强调旧 URL 兼容、首次任务成功率、误选率、点击数、前进/后退恢复率和真实 3011 视觉验收。

### 10.2 分歧点

| 议题 | consolidation 第十节 | 本报告 | 分歧理由 |
|---|---|---|---|
| 一级导航数量 | 10 个日常入口 | 6 个任务域 + 设置 | 既有方案完成了对象去重，但仍把“对象管理面”都放在一级。本报告以六条用户任务流组织二级视图，减少在全局应用侧栏之外再选择 10 个项目入口的成本。数据和动作没有被合并，只是层级下沉。 |
| 群聊与协作关系 | 群聊一级；协作关系下沉到“项目团队” | 同属“协作”的两个二级视图 | A2A 图回答“如何协作”，与成员生命周期/身份配置不同；与群聊共享协作心智更直接。若任务测试显示用户先从“谁参与”寻找关系图，则可采用既有归属。 |
| 工作区、里程碑、Git | 三个独立一级入口 | “交付”下的工作区、里程碑、版本历史 | 三者不合并页面，只共享交付域。用户在验收和追溯时经常沿“成果文件 → 交付节点 → 版本”连续移动，持久二级导航比三个一级入口更能表达链路。 |
| 项目成员与能力 | “项目团队”和“能力与权限”两个一级入口 | “团队”下的成员、能力清单、访问矩阵 | 能力对象与成员身份仍分视图；本报告只把它们放进同一团队管理域。既有方案更少一次点击，本报告更少一级选择，需用频率数据裁决。 |
| 运行与审计 | 运行控制和项目审计各自一级 | “活动”下的 Runs 与 Events | 两者明确不合并数据和动作；共享一级域是因为异常排查在“执行尝试”和“不可变事件”之间往返频繁。 |
| Git 仓库设置 | 保留在 Git 历史与恢复 | 移到“项目设置 > 仓库” | 远端、来源和初始化是低频高风险配置；提交/diff/分支/恢复是版本任务。3011 当前先铺仓库表单再进入 20 条提交历史，明显阻断追溯扫描。 |
| 工作项四分区 | 概览 / 执行记录 / 协作记录 / 成果与验收 | 摘要 / 活动 / 交付物 / 验收 | 3011 抽查中同一 session 在协作列表多次出现，执行和证据又重复会话内容。本报告按 Run 将事件/会话组装成“活动”，并把“交付物”和具有通过/退回动作的“验收”分开；既有方案则保留协作独立、合并成果与验收。 |
| 对象内关联记录 | 任务执行记录可完整分页；其他页摘要 | 所有对象上下文最多 3 条，完整分页只在活动 | 本报告更严格执行“每类集合一个全量浏览载体”，以避免工作项、成员、里程碑再次长成 Run 浏览器；代价是查看某任务的第 4 条旧运行需要深链活动页。 |
| 概览条目上限 | 第二轮预算为行动 3、问题 3 | 工作与异常各最多 5 | 都禁止分页。5 条更适合当前桌面密度并减少“查看全部”频次；若 5 条让首屏超过一个视口，应降为 3 条。 |

### 10.3 对分歧的建议裁决顺序

1. 先实现双方一致且风险低的去重：合并工作入口、合并能力入口、移除驾驶舱分页、移除 A2A 完整事件流、移除成员 Run 长列表、设置下沉。
2. 再用树测试比较“10 个对象入口”与“6 个任务域”的首次入口正确率。样本任务必须覆盖文件编辑、里程碑、版本恢复、审计取证和成员授权，不能只测任务创建。
3. 用 3011 数据做工作项详情原型 A/B：`执行 + 协作 + 成果验收` 与 `活动 + 交付物 + 验收`。重点测用户能否判断同 session 多次出现的原因，以及能否从验收条件快速找到证据缺口。
4. 若 6 域方案让高频用户多一次点击但入口误选显著下降，保留二级导航并支持记住每个域的最近视图；若没有降低误选，则采用 consolidation 的 10 入口结构。
5. Git 仓库配置是否下沉不应由导航偏好决定：单独测试“浏览最近提交”和“配置远端”两项任务，确认同屏表单是否影响版本扫描和误操作风险。

本报告的最终立场是：consolidation 已正确识别主要重复对象，但“10 个一级入口”仍偏向系统对象目录；“6 个任务域 + 唯一对象载体”更符合真实任务流，也给未来增加新的交付物、能力类型或事件类型留出层级空间。若实现资源有限，双方一致项应先落地，6 域层级可作为第二阶段导航重构。
