# 工作项单页详情产品迭代方案

> 日期：2026-08-25
>
> 适用范围：项目工作区中的单个工作项详情
>
> 产品原则：简单、高效、归一化；优先交付，不引入新的复杂模型

## 一、背景与问题

现有工作项详情把一项任务拆成五个页签：上下文与验收、执行与事件、相关对话、代码与文件变更、证据与审批。用户必须在多个页签之间来回切换，才能回答最基本的产品问题：这项任务要做什么、开始前还缺什么、现在进行到哪里、是否满足验收、下一步应该做什么。

这种拆分还带来三个直接问题：

1. 同一任务的状态、数量和进展在多个位置重复出现，信息来源不清晰。
2. 界面暴露了过多技术记录概念，项目负责人难以快速判断业务进度。
3. 每个页签都可以继续扩展，导致交互和实现复杂度持续上升，却没有提高任务交付速度。

本次迭代把工作项详情收敛为一个连续页面。底层已有记录仍可作为真实数据来源，但不再以五个并列产品入口呈现。

## 二、目标用户

- 项目负责人：快速判断任务是否有人负责、是否受阻、是否达到验收条件，并执行权限允许的分派、审批、退回或重开操作。
- 项目编辑者：理解目标和验收要求，更新允许编辑的字段，启动或推进任务。
- 项目查看者：只读了解任务目标、状态、证据和最近进展，不看到也不能触发写操作。
- 参与项目的数字员工：其工作结果以业务进展、交付物和验收依据呈现，不要求用户理解底层执行记录。

## 三、单一产品目标

用户进入一个工作项后，应在同一页面内完成以下判断并采取一个合适动作：

> 明确任务目标、开始条件、验收状态、下一步和最近进展，然后直接推进任务。

本次迭代不追求展示所有底层信息，也不重建一套新的任务系统。页面只保留完成上述目标所需的信息和操作。

## 四、删除五个页签的决定

工作项详情不再展示以下五个页签：

1. 上下文与验收
2. 执行与事件
3. 相关对话
4. 代码与文件变更
5. 证据与审批

删除页签不是把它们换成五个折叠面板，也不是在单页里复制五套完整浏览器。原有内容按用户任务重新归类：

- 目标、前置条件和验收要求进入任务主体。
- 当前最需要处理的事项进入“下一步”。
- 有业务意义的执行结果、讨论、交付物和验收依据进入“最近进展”。
- 需要查看完整记录时，通过明确的“查看全部进展”或精确结果链接进入现有对应位置。

## 五、信息优先级

### 第一优先级：识别当前任务

- 返回任务列表
- 任务标题
- 当前状态、优先级、负责人、更新时间
- 有编辑权限时显示“编辑任务”

### 第二优先级：决定下一步

- 一句与当前状态匹配的下一步提示
- 一个最主要的产品操作
- 必要时提供少量次要操作，不并列堆放多个同权重按钮

### 第三优先级：理解完成条件

- 任务目标
- 开始前需要
- 验收标准
- 真实验收状态与真实验收依据

### 第四优先级：了解最近变化

- 最近进展摘要
- 与具体结果、讨论、交付物或验收依据的精确链接
- 查看全部进展

## 六、最终页面结构

页面采用单一纵向阅读流，不再包含工作项内部页签。

1. **返回入口**：返回任务列表，并保留项目工作区上下文。
2. **任务页头**：标题、状态、优先级、负责人、更新时间；有权限时显示编辑入口。
3. **下一步卡片**：展示当前状态对应的下一步说明和一个主操作。
4. **任务目标**：用产品语言说明要达成的结果。
5. **开始前需要**：列出真实前置任务或条件；没有时明确显示“无需前置任务”。
6. **验收与依据**：展示验收标准、等待验收或已通过状态、真实依据数量；没有依据时显示等待状态。
7. **最近进展**：最多展示三条去重后的最新进展，分别覆盖最新执行、真实讨论和交付成果，按最新在前排列。
8. **查看全部进展**：仅在存在可到达的完整进展入口时显示。

桌面宽度采用“任务主体 / 最近进展”主次双列；任务目标、开始前需要和验收标准保持同一纵向阅读流。窄屏自动改为单列，信息顺序在所有尺寸上保持一致。

## 七、各状态的下一步与操作

页面只显示后端真实支持且当前用户有权限执行的操作。没有真实命令或没有权限时，不展示伪按钮。

| 状态 | 下一步提示 | 主要操作 | 可选辅助操作 |
| --- | --- | --- | --- |
| 未指派 | 先指派一位数字员工，明确由谁推进这项任务。 | 指派负责人 | 编辑任务 |
| 待处理 | 确认任务目标和验收标准，然后开始推进。 | 开始推进 | 编辑任务 |
| 执行中 | 持续推进任务，并补充可核验的工作结果。 | 查看进展 | 仅在真实流程支持时提交验收 |
| 阻塞 | 先解决当前阻塞原因，再继续推进。 | 查看阻塞原因 | 仅在真实流程支持且有权限时重试或恢复 |
| 待验收 | 对照验收标准核对结果和依据。 | 通过验收 | 退回修改 |
| 完成 | 查看最终交付物；确需继续时再重新打开。 | 查看交付 | 有权限时重新打开 |

状态提示描述用户下一步，不复述技术状态机。主要操作在一个状态下保持唯一，防止用户猜测应该点哪个按钮。

## 八、编辑模式

- 编辑在当前页面完成，不新增编辑页签，也不强制跳转到独立页面。
- 本次迭代仅编辑当前权威接口已经支持的字段，至少包括负责人、状态和优先级；不因页面改造推定标题、描述或验收标准已经支持写入。
- 点击“编辑任务”后进入明确的编辑态，显示“保存修改”和“取消”。
- 不使用自动保存。未保存内容只保留在当前编辑态，取消后恢复已保存值。
- 保存失败时在当前区域说明原因，保留用户尚未提交成功的内容，便于重试。
- 保存成功后以服务端返回结果刷新页面，服务端仍是状态和权限的权威来源。
- 查看者永远不进入编辑态，不渲染写操作控件。

## 九、验收与证据真实性

验收信息必须来自真实、持久化且与当前工作项关联的数据。

- 验收标准来自工作项的权威字段，不从标题、描述或状态推测。
- 只有实际存在的关联依据才计入依据数量并显示。
- 请求中的文件名、说明文字、任务状态或界面展示本身都不等于验收依据。
- “完成”状态不自动等于“已通过验收”。通过验收必须有真实流程结果和有权限用户的操作。
- 缺少依据时显示“等待验收依据”，不得用示例数据、推测结果或占位记录制造已完成印象。
- 页面可以用更自然的产品文案汇总底层数据，但不得改变其类型、归属和结论。

## 十、最近进展规则

- 最多显示三条，按最新在前排列；优先各保留最新一条执行、真实讨论和交付成果，避免同类记录挤占全部空间。
- 只展示与用户判断任务进展有关的内容，并归为执行结果、讨论、交付物、验收依据四类。
- 同一业务进展按稳定的业务身份去重，避免同一结果在多个来源中重复出现。
- 每条进展包含可理解的摘要、发生时间和类型；不直接展示内部编号或底层记录术语。
- 只有存在精确目标时才显示“查看结果”“查看讨论”“查看交付”或“查看依据”。
- 链接必须到达当前工作项的对应内容；无法精确到达时不提供误导性链接。
- “查看全部进展”用于进入已有的完整记录入口，不在单页重新实现完整执行、对话、文件或审计浏览器。

## 十一、空状态

| 场景 | 产品行为 |
| --- | --- |
| 没有负责人 | 下一步提示指派负责人；有权限者看到指派操作，查看者只看到未指派状态。 |
| 没有前置任务 | 显示“无需前置任务”，不留空白区域。 |
| 没有验收标准 | 有权限者看到补充标准的提示；查看者看到“尚未定义验收标准”。 |
| 没有验收依据 | 显示“等待验收依据”，不得显示已通过。 |
| 没有最近进展 | 显示“尚未开始”，不填充示例动态。 |
| 没有可用完整入口 | 隐藏“查看全部进展”，不跳到不相关页面。 |
| 链接对象已不存在或不可访问 | 安全返回任务列表或显示明确不可用状态，不打开其他任务。 |

## 十二、权限差异

权限由服务端返回的项目访问角色和具体操作结果决定，前端不自行推导或扩大权限。

- 项目负责人：可以看到服务端允许的管理、分派、审批、退回和重开操作。
- 项目编辑者：可以编辑普通工作项字段，并执行服务端允许的推进操作；负责人专属操作仍不显示。
- 项目查看者：只读查看任务、验收和进展，不显示编辑、开始、通过、退回、重开等写操作。
- 已离开或失效的历史成员信息可以作为历史归属展示，但不能成为新的负责人选项。
- 即使前端误显示某个操作，服务端也必须继续拒绝未授权请求；界面隐藏不是权限边界。

## 十三、中英文术语原则

可见文案优先使用用户熟悉的项目管理语言，并在中英文之间保持同一含义。

| 中文 | 英文原则 |
| --- | --- |
| 工作项 / 任务 | Task 或 Work item；同一上下文保持一致 |
| 任务目标 | Task goal |
| 开始前需要 | Before you begin |
| 验收标准 | Acceptance criteria |
| 验收依据 | Acceptance evidence |
| 最近进展 | Recent progress |
| 数字员工 | Digital Employee |
| 项目负责人 | Project owner |

可见文案不得出现 Run、Event、Session、Commit、ID 等底层技术术语，也不使用“运行时”“持久化”“原子操作”等实现语言。中英文都必须是自然产品文案，不暴露翻译键，不残留未替换参数。

## 十四、响应式行为

- **1920 像素**：内容保持舒适阅读宽度，不随屏幕无限拉伸；下一步和关键信息仍靠近视觉中心。
- **1280 像素**：完整呈现桌面布局，不产生页面级横向滚动。
- **768 像素**：并列内容按阅读顺序折为单列，主要操作仍紧邻下一步说明。
- **390 像素**：全部内容单列；返回、编辑和主要操作可触达，不被固定导航遮挡，不出现横向溢出。

本页不引入需要横向滚动的大表格。长标题、人员名称和进展摘要应换行或截断，并提供可访问的完整信息。

## 十五、可访问性

- 使用连续且正确的标题层级，列表和任务属性采用合适的语义结构。
- 所有操作均可通过键盘到达和触发，焦点样式清晰可见。
- 状态不能只靠颜色区分，同时提供文字或图标含义。
- 文本和背景使用产品设计令牌并满足项目既有对比度标准。
- 移动端主要操作尽量提供不小于 44 像素的触摸目标，其他控件不得低于项目通用标准。
- 进展链接使用能说明目标的名称，不使用多个含义不明的“查看”。
- 保存、失败和状态变化需要有可感知反馈，不能只通过短暂颜色变化表达。

## 十六、明确不做

- 不新增后端实体、数据模型、专用详情协议或证据类型。
- 不新增五个替代页签、五个大型折叠区或新的二级导航。
- 不在工作项单页复制完整执行记录、对话、代码、文件、提交或审计浏览器。
- 不在客户端推导权限、验收通过或证据真实性。
- 不为本次页面改造拆分现有接口、重做服务端分页或重构全局状态管理。
- 不进行整个项目工作区的视觉重构，也不扩展为全站字号整改。
- 不把真实项目的跨域验收纳入本次迭代；该验收后续单独进行。

## 十七、旧链接的产品行为

- 旧的 `tab=detail` 链接作为只入不出的兼容入口，打开后归一到当前工作项区域 `tab=work`。
- 旧链接包含工作项时保留该工作项；不包含工作项时回到任务列表。
- 旧的 execution、conversation、changes、review 子页签分别定位到单页中对应的执行进展、讨论、变更或验收区域；兼容完成后不再生成旧子页签参数。
- 已废弃或未知的子页签值不创建新入口，直接打开工作项单页顶部。
- 工作项不存在、无权访问或链接状态失效时，清理过期选择并安全返回任务列表或显示明确错误，不得误开其他工作项。
- 刷新、前进和后退应保持当前工作项及归一后的地址；浏览器行为需要在本地环境单独验收。

## 十八、产品验收标准

1. 从任务列表进入任一工作项后，只看到一个连续详情页面，不出现五个工作项内部页签。
2. 用户无需切换页面即可看到任务目标、开始前需要、验收状态、下一步和最近进展。
3. 每种状态都有明确且唯一的主要下一步；只展示真实存在并有权限执行的操作。
4. 查看者全程只读，不能看到或触发任何写操作。
5. 验收状态和依据数量完全来自真实关联数据，不从任务状态或展示内容推测。
6. 最近进展最多三条、最新在前、无重复，链接只指向当前任务的精确目标。
7. 中英文产品文案完整自然，不出现底层技术术语、翻译键或未替换参数。
8. 旧链接能安全归一到工作项单页，工作项身份不丢失，地址不再生成已废弃入口。
9. 1920、1280、768、390 四个宽度下均无页面级横向溢出，主要操作可触达。
10. 页面可使用键盘完成浏览和允许的操作，焦点、状态和操作反馈可感知。
11. Docker 内的类型检查、相关合同测试和构建通过，并完成本地 3011 端口的中英文、权限与浏览器回归验收。
