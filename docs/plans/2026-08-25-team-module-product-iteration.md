# 团队模块产品归一化方案

> 日期：2026-08-25
>
> 范围：项目工作区“团队”模块
>
> 原则：简单、高效、归一化；优先交付，不扩建新的后端模型

## 一、背景与问题

团队模块原本同时承载项目成员、单成员运行谱系、项目配置、能力卡片、项目工具、重复的能力范围入口，以及 L1/L2/L3 和 13 项项目级审批策略。用户进入团队后，必须先理解“成员快照、运行节点、能力绑定、工具基线、自主级别”等实现概念，才能回答两个最基本的问题：

1. 谁在负责和参与这个项目？
2. 每位数字员工在当前项目中能做什么？

原结构的主要问题不是功能不足，而是相同信息被多个入口和多个组件重复表达：

- “项目成员”实际管理数字员工，却容易被理解为人类项目协作者。
- 成员页的三张统计卡、两组成员列表、谱系图、三层说明和技术事实重复表达同一批成员，挤占了协作关系与职责详情的注意力。
- 能力中心和能力矩阵是同一能力数据的两个二级入口。
- 项目工具基线、工具卡片底部说明和工具矩阵再次重复“谁能使用什么”。
- 成员写操作和能力写操作曾使用不同的人类权限口径。

本次迭代不新增能力权限引擎，也不重建成员接口，只收敛现有信息架构和界面任务。

## 二、目标用户

- 项目负责人：组建数字员工团队，指定执行负责人，调整项目内工作设置和能力。
- 项目编辑者：查看数字员工职责、在岗状态和能力范围，但本次不承担团队配置写操作。
- 项目查看者：只读了解团队分工和能力范围。
- 项目数字员工：作为项目执行成员展示，其职责、状态和可用能力均以当前项目为边界。

人类项目共享成员不是本模块的管理对象。人类访问范围继续归“项目设置 > 访问”，避免把项目访问授权和数字员工执行配置混在同一团队界面。

## 三、单一产品目标

团队模块只完成一个任务：

> 明确由谁推进项目，并让用户看清每位数字员工在当前项目中的职责和能力。

任何不能直接帮助完成该任务的运行历史、技术谱系、内部事实和重复权限视图都不进入默认页面。

## 四、最终信息架构

```text
团队
├─ 数字员工（默认）
│  ├─ 协作网络（置顶、唯一成员选择入口）
│  └─ 所选数字员工详情（直接展开）
│     └─ 配置 / 工具 / MCP / Skill
└─ 能力
   ├─ 能力清单（默认）
   └─ 可用范围
```

团队顶层只保留“数字员工”和“能力”两个二级入口。“能力矩阵”不再是独立入口，而是能力页内部的一种查看方式。

## 五、删除与保留决定

### 从数字员工默认页删除

- 三张成员统计卡。
- 单成员运行/快照谱系图和运行图例。
- “源数字员工、项目快照、执行冻结记录”三层说明。
- 快照代次、源状态、继承能力数量、关闭工具数量等技术事实。
- 默认展开的大型工作设置表单。
- 在岗与已退出两组成员列表及其分页；成员状态改由协作网络节点和详情表达。
- “编辑工作设置”展开按钮；选择节点后直接显示对应数字员工详情。
- 整套 L1/L2/L3 自主级别、13 项审批策略表单、说明、计数及相关项目级文案。
- 成员页内的完整活动或运行列表。

这些内容的删除不改变底层数据。完整活动继续由“活动”域负责，工作设置在所选数字员工详情中呈现，不再由单独按钮展开。

### 从能力页删除

- 独立“能力矩阵”二级入口。
- 项目负责人和普通成员的工具基线统计卡。
- 项目工具卡片中重复的底部状态与适用成员说明。
- 独立入口中重复呈现的项目工具矩阵；项目工具仍保留在能力页“可用范围”的统一矩阵中。
- 能力为空时仍展示的无意义类型和来源筛选。

### 保留

- 协作网络，用于查看团队成员之间的协作关系与分工；不包含运行节点或完整活动。
- 点击网络节点后直接展开的数字员工详情，包括姓名、项目职责、执行负责人、在岗状态、员工类型和工作设置。
- 创建、编辑、设置负责人、停用或移出、恢复、升级等现有真实操作。
- 项目专属数字员工“升级为标准数字员工”的唯一主界面直接入口。
- 精确进入当前数字员工全部活动的入口。
- 主模型、备用模型、最大工具轮次和项目专属指令等现有工作设置。
- 每位项目数字员工独立的配置、工具、MCP 和 Skill 入口，以及各自真实状态。
- 能力清单与可用范围两种查看方式。
- 旧链接兼容和 URL 中的筛选、分页、成员选择状态。

## 六、数字员工默认页

### 页面优先级

1. 页面标题和一句说明。
2. 创建数字员工主操作，仅项目负责人可见。
3. 协作网络置顶，作为唯一成员选择入口。
4. 所选数字员工详情直接展开；切换节点即切换详情。
5. 详情中的查看活动、身份、升级和工作设置等真实操作。

页面不再渲染在岗与已退出成员列表。协作网络节点与所选详情只保留完成选择和判断所需的信息：

- 名称
- 项目职责
- 在岗或已退出
- 是否为执行负责人
- 项目专属数字员工或标准数字员工

### 职责优先原则

团队页面不是身份资产浏览器。所选数字员工详情必须优先说明“负责什么”，而不是先展示来源、目录、内部状态或历史数量。

项目负责人和数字员工执行负责人是两个不同概念：

- 项目负责人是有权管理团队的人类用户。
- 执行负责人是负责组织项目推进的数字员工。

界面不得用同一个“负责人”标签同时指代两者。

### 协作网络

协作网络必须保留，但它与已删除的单成员运行谱系图不是同一对象。

- 节点只表示数字员工。
- 至少区分执行负责人、在岗和已退出状态。
- 连线只表达已有成员关系或协作关系，不展示运行、事件、会话或技术标识。
- 协作网络置于页面首要内容区，是唯一成员选择入口，不再与在岗/已退出列表并列。
- 点击节点直接展开该数字员工详情；切换节点时复用同一详情区并切换内容，不打开第二套页面。
- 层级固定为执行负责人在上、其他成员在下，首先表达组织分工，再表达成员间真实协作。
- PC 端下层成员沿横向展开，避免把同级关系误画成纵向流程；节点适当放大，保证名称、职责和状态可读。
- 画布围绕实际节点和连线收紧，减少顶部、底部和两侧无信息留白，不用大画布制造复杂感。
- 图中没有可用关系数据时仍展示成员节点或明确空态，不推测连线。
- 图上方提供“查看协作记录”，精确进入现有审计页的协作记录过滤结果。
- 完整活动继续跳“活动”域，协作网络不得重新长成活动时间线。

## 七、数字员工详情直接展开

用户在协作网络选择数字员工后，页面直接展开唯一的数字员工详情区。页面删除“编辑工作设置”按钮；工作设置随详情呈现，项目负责人可在详情内修改和保存，其他用户只读查看。

单一详情区有三个产品作用：

1. 协作网络负责选择，详情负责查看和操作，不再由列表和展开按钮重复导航。
2. 切换节点只切换同一详情区的内容，不创建多个成员面板。
3. 已退出成员的历史信息保持只读，不制造可编辑假象。

设置内容继续使用现有权威能力：

- 主模型和备用模型
- 最大工具轮次
- 项目专属指令

数字员工详情不再提供项目级审批策略配置：

- 删除 L1 自动执行、L2 通知、L3 审批的选择机制。
- 删除 13 项策略字段、每项说明、策略数量和空策略说明。
- 删除只服务于这套项目详情表单的中英文文案，不在详情中留下只读摘要或折叠入口。
- 本轮只移除项目详情的重复配置面；平台底层对高风险或受限操作的安全拦截继续保留，其他产品场景的审批能力不受影响。

保存只影响当前项目。失败时保留真实服务端状态并展示错误，不假定源数字员工已经改变。

### 升级入口

项目专属数字员工的“升级为标准数字员工”是必须保留的直接产品能力：

- 选择在岗的项目专属数字员工后，项目负责人可在成员主界面直接看到升级入口。
- 升级入口是唯一入口，不再同时出现在工作设置、身份编辑抽屉或多层菜单中。
- 点击后仍使用现有确认对话框说明复制范围和“不改变当前项目数字员工”的结果。
- 已退出员工、标准数字员工、编辑者和查看者不显示升级入口。
- 升级成功后提供打开新标准数字员工的结果入口，当前项目数字员工保持不变。

## 八、数字员工状态与动作

| 状态 | 页面表现 | 项目负责人动作 | 其他用户 |
| --- | --- | --- | --- |
| 在岗成员 | 可参与任务和项目协作 | 在详情中调整工作设置、设为执行负责人、停用或移出、查看活动 | 查看职责与活动 |
| 在岗执行负责人 | 标记为当前执行负责人 | 在详情中调整工作设置、查看活动；转交后才能停用 | 查看职责与活动 |
| 已退出 | 历史只读，不再接收新任务 | 恢复、查看历史活动 | 查看历史职责与活动 |
| 项目专属数字员工 | 身份和设置属于当前项目 | 在主界面直接升级为标准数字员工、编辑身份 | 查看 |
| 标准数字员工成员 | 当前项目保存其项目内设置 | 调整项目内工作设置、移出或恢复 | 查看 |

所有动作都必须调用已有真实服务能力。没有服务端能力时不显示按钮，不用前端状态模拟成功。

## 九、活动边界

成员页不再复制完整活动列表或运行图。点击“查看完整活动”后：

- 进入现有“活动”域。
- 携带当前数字员工过滤条件。
- 清理上一页不属于活动域的分页和对象状态。
- 刷新后保持该成员过滤。

成员页只回答“谁负责什么”，活动页回答“具体发生了什么”。

## 十、能力页

能力页内部提供两种视图：

- **能力清单**：查看和管理现有项目能力与项目操作工具。
- **可用范围**：横向比较已绑定项目能力对各数字员工的可用状态。

两种视图共享同一个能力入口和 URL 状态，不再作为两个团队二级导航项。

### 能力清单

- 有 Skill 或 MCP 绑定时，显示类型和来源筛选。
- 没有 Skill 或 MCP 绑定时，隐藏筛选和空白能力区，直接展示仍然存在的项目操作工具。
- 选择数字员工后，项目操作工具显示该员工当前有效数量和逐项状态。
- 工具卡片只展示名称、说明和一个真实状态或开关，不重复适用成员 footer。
- 不再展示项目负责人/普通成员两张基线卡。

### 工具文案规则

本轮新增工具的名称、说明和依赖关系必须使用中立、事实型语言：

1. 用途：该工具解决什么明确任务。
2. 真实对象状态：仅说明与操作判断直接相关的对象和当前状态。
3. 真实约束：仅在实际存在时补充依赖关系或角色边界；没有真实前置条件时不写前置说明。

工具文案不得使用“需要当前成员具备访问权限”“当前成员可访问”等泛化权限兜底；只有存在真实角色限制时才准确写明角色边界。文案不得出现内部模块、函数、数据库、协议、调度、存储或其他实现细节，不得使用口语化、拟人化、口号式表达，也不得保留无法帮助用户判断是否使用该工具的空泛说明。依赖关系只说明真实对象或用户可理解的先后条件，不解释内部调用链。中文与英文必须逐项表达相同事实、条件和结果，不允许一侧增加承诺或遗漏限制。

### 可用范围

- 统一比较已有能力绑定、项目操作工具与数字员工之间的有效范围，与能力清单覆盖同一数据域。
- 已退出员工保持历史列并明确不可用。
- 没有明确分配结论时显示“按项目设置”，不得推测为可用。
- 可用范围复用既有统一矩阵呈现能力与项目操作工具，不再维护遗漏项目工具的平行实现。
- 项目操作工具的写操作继续在能力清单按成员配置。
- 可用范围用于比较，写操作仍集中在能力清单。

## 十一、能力状态

| 状态 | 含义 | 操作 |
| --- | --- | --- |
| 可用 | 当前项目和成员配置均允许 | 项目负责人可关闭 |
| 已关闭 | 当前项目主动关闭 | 项目负责人可启用 |
| 项目策略限制 | 上层策略不允许 | 只读，不提供无效开关 |
| 项目设置限制 | 当前成员项目设置不允许 | 只读或前往该员工工作设置 |
| 仅执行负责人可用 | 普通成员没有该项目操作 | 只读 |
| 已退出 | 员工历史能力冻结 | 需要时先恢复成员 |
| 按项目设置 | 当前数据没有明确单成员结论 | 只读，不显示为等待或可用 |

## 十二、成员能力包与模板 Skill 生命周期

### 成员独立能力包

每个项目数字员工独立拥有一套能力包，并在同一数字员工详情中提供“配置 / 工具 / MCP / Skill”四个直接入口。这些入口不扩成新的团队顶层导航，也不与能力页的全项目清单重复：成员详情回答“这位数字员工当前带什么”，能力页回答“整个项目有哪些能力以及覆盖谁”。

- 配置只影响当前项目中的该数字员工。
- 工具和 MCP 沿用平台提供的能力，是项目数字员工对平台依赖的引用；项目不复制一份假资源。
- Skill 加入项目数字员工时复制为当前项目资产。复制完成后由项目独立管理，后续编辑、启停或删除不追随来源变化，也不反向修改来源。
- 同一项目内不同数字员工可以拥有不同的配置、工具、MCP 和 Skill 组合，不通过一个共享开关隐式覆盖全部成员。

### 运行冻结

每次运行开始时保留该数字员工当时的配置与能力版本，包括工具、MCP 和 Skill 的当次有效组合。运行开始后的成员配置或能力变更只影响后续新运行，不改写正在进行或已经完成的运行记录。用户查看历史时应能知道当时使用了哪一版配置与能力，但页面不展示内部版本结构。

### 成员退出

数字员工退出项目后不再接收新任务，但其历史运行、配置记录和已经形成的项目 Skill 资产继续保留，用于审计、复盘和模板选择。退出不会删除其他成员仍在使用的项目资产，也不会把项目内独立修改同步回来源。

### 发布项目模板

发布模板时按能力类型采用不同规则：

- 工具和 MCP 只发布中立依赖声明，说明用途、真实依赖和必要角色边界，不携带平台资源副本、凭证或个人授权。
- Skill 必须逐项选择是否随模板携带文件，默认全部不携带。
- 未选择的 Skill 不进入模板；发布前明确列出每个未选 Skill 会影响的数字员工，避免用户误以为模板仍包含完整能力。
- 已退出成员关联的项目 Skill 也按同一逐项选择规则处理，不因成员退出而静默丢失或默认携带。

### 从模板创建项目

- 模板中选择携带的 Skill 文件复制为新项目自己的资产，创建后与模板来源独立管理。
- 工具和 MCP 依赖在新项目中逐项核对可用性，并明确显示可用、缺失或受限；核对不等于自动安装、自动授权或借用发布者资源。
- 依赖不可用时保留清晰缺口和受影响数字员工，用户补齐依赖前不得把对应能力显示为可用。
- 未随模板携带的 Skill 不在新项目中创建空壳、占位能力或虚假可用状态。

### 权限与文案

项目负责人可以调整成员能力包并决定模板 Skill 携带范围；编辑者和查看者只读。产品文案只说明能力用途、项目归属、真实依赖、携带状态和受影响成员，不解释内部复制、版本、存储或关联实现。

### 工具选择与全局名称归一

成员能力包不使用浏览器原生长下拉承载平台工具，也不另建项目专用工具选择器。项目成员详情的「工具」和「Skill」两个 Tab 直接复用原有 Agent 对应 Tab 的页面内容、组件和交互，项目页只传入成员对应的 Agent、项目权限与必要上下文；不得复制 JSX/CSS、另做相似面板或保留平行实现。此前新增的项目侧紧凑选择器属于被否决的过渡方案，必须删除，不作为最终资产保留。

复用不仅是视觉复用。项目 Agent 的 Skill Tab、项目运行和模板发布必须读取同一个项目 Agent 工作目录；不得让原有 Skill 页写入独立 Agent 目录后，再通过复制或双向同步维持第二套项目 Skill 文件。项目能力关联仅记录归属、启用状态和模板选择，不重复保存文件正文。

项目成员能力包、标准数字员工工具配置和公司级工具配置共用同一套用户显示合同：底层稳定标识保持不变，界面名称与说明统一做中英文适配。名称说明能力用途，说明文字只补充必要依赖或使用边界；不展示类名、函数名、内部通道、存储结构、协议实现或口语化解释。任何新增工具必须先补齐这套显示合同，不能只在单个页面临时翻译。

共享工具面板的状态和操作文案也属于同一显示合同，包括始终可用、启用、停用、配置、来源和可用性；不得只翻译工具名称与说明而保留英文状态硬编码。

直接复用的 Agent Skill Tab 及统一文件操作区同样必须完成全链路中英文适配。导入来源、市场浏览、预设选择、搜索、安装、上传、新建、加载、空状态、成功/失败反馈和弹窗操作不得残留英文硬编码；修正必须落在原共享组件，使 Agent 与项目成员两处同时生效，禁止在项目页覆盖文案。

共享工具面板的搜索框使用统一输入布局：搜索图标占用固定前置区域，输入文字和 placeholder 从图标之后开始；中文、英文、空值、聚焦和窄宽度下都不得重叠。该规则只在共享工具面板修复一次。

### 项目列表密度

项目列表继续使用紧凑信息行，但列表容器必须保留稳定的纵向间距，使卡片边界、状态和点击范围清晰可辨。间距由列表/网格容器统一控制，不在单张卡片逐项补边距；桌面与移动端沿用同一密度规则，筛选切换和列表/网格切换不得造成卡片粘连或间距跳变。

## 十三、权限归一

本次迭代采用最小一致规则：团队模块所有写操作仅项目负责人可用。

- 项目负责人：创建、编辑、设置执行负责人、停用、移出、恢复、升级、保存工作设置、启停能力和项目操作工具。
- 项目编辑者：只读查看数字员工和能力。
- 项目查看者：只读查看数字员工和能力。

前端是否显示操作只依赖服务端返回的项目访问角色；服务端继续作为最终权限边界。后续若确需向编辑者开放部分团队管理，应先建立明确动作权限合同，不在本次迭代中扩建。

### 项目设置横向设置区

项目设置页在同一页面收敛为“访问范围”和“运行设置”两段横向设置区，不使用两张大卡片。每段左侧放标题与必要说明，右侧放对应控件，段与段之间使用细分隔线；窄屏按标题说明在前、控件在后的顺序切换为单列。

- **访问范围**：共享项目使用多选管理共享成员与其角色，并在同组控件中从已选共享成员里单选运行身份。共享成员选择强制复用统一 `OrgMemberAccessPicker`，候选人只来自统一组织成员目录；不得读取 bootstrap 结果，也不得在项目页面自造人员下拉、缓存或第二套搜索。
- **运行设置**：只承载仍然有效的项目运行参数。项目审批选择从此区删除；循环保护作为与其他输入控件一致的标准行控件，使用相同标签、说明、输入、校验、禁用和保存反馈结构，不单独制作强调卡或技术说明块。

两段设置区使用同一标题层级、字段间距、错误反馈和保存动作。项目设置页移除审批选择不代表关闭平台安全能力；底层高风险安全拦截继续生效。

### 共享项目运行身份

访问项目与代表谁运行是两个独立决定：

- 共享成员是“访问范围”中的多选，决定哪些人可以进入项目及其项目角色。
- 共享项目必须在“访问范围”中与共享成员同组手动单选一名运行身份；候选人只来自当前已选共享成员，不自动猜测，也不允许留空。
- 私有项目不提供运行身份选择，固定使用项目负责人。
- 如果用户从访问范围移除了当前运行身份，页面必须要求重新选择后才能保存，不静默切换到其他成员。
- 共享成员与运行身份作为一组设置保存。任一项不合法时整组不生效，不出现访问范围已变更但运行身份仍无效的部分成功。

每次项目运行开始时，都保留当次使用的运行身份，同时继续记录真正触发这次运行的人。之后即使项目设置变化，已有运行仍使用启动时保留的运行身份；该运行及其后续自动协作均使用这一身份已授权的资源，不借用实际发起人或后来切换成员的授权范围。产品界面只解释“运行身份”“实际发起人”和授权结果，不展示数据字段、关联结构或内部实现。

## 二十、项目数字员工设置隔离与默认能力

- 项目数字员工是当前项目的独立资产。模型、指令、工具、MCP、Skill、身份设定、核心记忆和各能力配置只在当前项目生效，任何项目页面操作都不得修改来源数字员工或公司级配置。
- 从标准数字员工创建时执行复制，不建立可反向修改来源的共享设置。来源只用于生成初始项目资产；复制完成后，两边独立演进。
- 项目工具继续复用标准数字员工的“工具”界面和同一开关逻辑，不新增工具选择器；项目页只展示普通平台工具，MCP 在独立 MCP 入口管理。

## 二十五、生产验证反馈收口（2026-08-27）

生产切换后的项目创建验证新增以下交付项，全部沿用既有组件和数据合同，不增加平行实现：

1. 项目列表的列表/网格切换按钮使用统一方形点击区，图标在水平与垂直方向居中。
2. 创建项目第一步返回并展示数字员工真实头像；站内受保护头像沿用现有鉴权资源展示方式，加载失败才回退为首字占位。
3. 数字员工选择区增加名称和岗位说明搜索；筛选不改变已选成员、负责人和默认能力。
4. 创建项目第二步只展示第一步已经选择的数字员工。选择成员后，在同一区域切换该成员的“工具 / 技能”面板；目录、分组、搜索与多选状态复用标准数字员工已有的通用能力目录组件。
5. 第一阶段选择成员时已经带入项目默认能力；第二步是可选确认步骤，用户不修改工具或技能也可以直接进入下一步并创建项目。
6. 项目共享工具、MCP 或 Skill 继续保存为项目范围能力，并在通用面板中以中立来源标签区分；不新增第三套能力入口。
7. 创建向导左侧步骤连接线与圆形步骤标记使用同一中心轴，三个步骤在桌面端保持对齐。
8. 修复本地存储模式下项目创建将 Agent 目录物化回自身的问题。本地 AgentDir 直接作为来源目录读取，远端存储才执行物化；不得修改 AgentData 权限、不得复制运行缓存、不得写回来源数字员工。
9. 项目初始化接口补齐数字员工头像以及工具分类和 MCP 来源信息，供通用面板直接使用，不由前端猜测。
10. 修复多工具 Turn 在每个工具边界残留一个“思考中”加载态的问题。同一逻辑 Turn 只显示一个最新实时状态；已经完成的工具调用继续合并为一条可展开的执行记录，最终回复到达后实时状态消失。

本节验收条件：真实头像可见；可通过搜索定位成员；第二步切换成员后只显示该成员及项目共享的能力；不修改能力可继续创建；创建请求成功进入规划；来源数字员工目录内容和权限保持不变；多工具 Turn 任意时刻只有一个“思考中”状态；中英文界面无新增缺失文案。

## 二十六、生产验证反馈第二轮收口（2026-08-27）

1. 创建项目成员卡片的首字头像使用统一头像盒模型；成员正文使用明确类名，不得以通用子元素选择器覆盖头像布局。图片加载失败后的首字必须水平、垂直居中。
2. 探索页不再首屏或定时请求全量 `/api/agents/` 与全量 `/api/org/users`。统一使用一个轻量分页目录接口，仅返回卡片所需字段并直接携带创建者名称。
3. 探索目录在服务端完成可见范围、状态、关键词、排序和分页；默认每页 24 项，搜索输入合并短时间内的连续变更。全局 Agent 侧栏复用同一轻量目录数据，不再常驻请求完整 Agent 配置；旧 Agent 与组织成员接口合同保持不变，其他页面不受影响。
4. 创建项目第二步继续直接使用标准数字员工工具页已经使用的 `ToolCatalogPanel`，不得复制目录、分组、搜索、展开或选择实现。向导仅提供已选 Agent 与项目能力上下文。
5. 能力目录采用单一内部滚动区：搜索与工具/技能切换保持可见，分类展开后内容在可用高度内滚动，不被向导底部裁切；页面不产生嵌套失效滚动。
6. 用户在第一步选择成员后，第二步默认展示已选成员和已经带入的能力；不修改任何工具或 Skill 可直接进入下一步并创建项目。
7. 会话抽屉输入区空内容和单行内容垂直居中；多行内容向上扩展，附件与发送按钮保持稳定。该规则同时适用于普通文本和项目群聊富文本输入。
8. 项目规划与项目群聊不维护独立消息渲染器。历史消息、流式正文、思考过程、工具事件和完成归并统一使用标准 WebChat 的 `ConversationTimeline` 与 `chatTimeline` 合同。
9. 项目运行只增加标准流式事件到项目群会话的传输映射；事件类型与内容结构保持 WebChat 合同。不同数字员工的并发流使用稳定消息标识和发送者信息，不互相合并。
10. 后台轮询历史记录时使用通用历史合并逻辑，不覆盖正在流式输出的临时消息；持久化回复到达后归一为同一条最终消息。

本节验收条件：头像首字居中；探索首屏仅请求一个轻量目录接口且响应最多 24 项；成员总数增加不再放大全量响应；能力分类可展开并在面板内滚动；第二步可无修改继续；抽屉空、单行和多行输入布局正确；规划讨论中正文与思考过程随标准事件实时显示，完成后不残留“处理中”或重复回复。
